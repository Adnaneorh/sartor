## Solutions & lessons
<!-- How each issue was fixed, and what to remember next time. Reference related notes in docs/learning/ by wikilink once they exist. -->
- 2026-07-11 · AUDIT #5 resolved (all six findings, same day):
  (1) LOW-MED stamp-once — the read-then-write is GONE: `savePersonaAction` updates the persona fields and reads `onboarded_at` from that update's own RETURNING row; first-completion stamping is a second UPDATE guarded IN THE QUERY (`.is("onboarded_at", null)`), so only a never-stamped row can match — races and bad reads can no-op (0 matched rows is success) but can never overwrite the fact. PROVEN behaviorally: `scripts/persona-probe.mts` stamps twice with distinct sentinel timestamps — the first lands, the re-stamp matches 0 rows, the first timestamp survives; a seeded guard-drop flips both checks to FAIL (tester tested).
  (2) LOW missing-row loop — PGRST116 on the update now RECOVERS by inserting the row under `profiles_insert_own` (with a Sentry warning that the signup-trigger invariant broke); any other Postgrest error is Sentry-captured before the generic user message, and a failed recovery states it explicitly instead of looping "could not save".
  (3) LOW decision numbering — canonical = the DECISIONS.md 2026-07-11 clause numbers; every code/migration comment now cites `DECISIONS 2026-07-11 §n` (§1 dataset params, §3 enums, §4 onboarded_at, §5 salary), and the entry gained a numbering note mapping the historical plan numbering (the change-log plan lines above stay untouched as approved history; read them via plan-1→§4, 2→§3, 3→§1, 4→§5).
  (4) LOW two-account gap — the audit's ad-hoc cross-account test is committed as `scripts/persona-two-account-probe.mts`: A cannot read B; A's targeted update of B in the exact savePersonaAction shape incl. an onboarded_at overwrite → 0 rows + PGRST116; bulk `.neq` → 0 rows; B byte-identical after (service-role read); positive control A→A lands. Extended same day after Adnane's rule-13 review of the recovery insert: A's recovery-shaped insert for a ROWLESS third user is rejected by profiles_insert_own with exactly 42501 (rowless so a PK conflict can't mask the RLS verdict), and the same shape DOES restore A's own admin-deleted row with onboarded_at starting null. 7/7 PASS live; seeded RLS-hole simulations (service-role as the attacker, on the update and on the insert) each flip checks to FAIL (tester tested).
  (5) INFO check-docs — sections 4/5 now verify the persona enum lists (parsed from persona.ts, matched verbatim in DECISIONS.md and this file), the dataset city TOTAL against every "N cities" claim in DECISIONS/ROADMAP, and JSON codes == `PROVINCE_CODES` (the `as ProvinceCode` cast rests on that agreement). Three seeded defects (470 count, "office" enum, "XX" code) each FAILED with a precise message, reverted, green.
  (6) INFO niggles — `SALARY_MAX_CAD` is exported once from the schema and clamps the salary inputs, so the UI can't carry a value the boundary rejects; `desired_roles` are deduped case-insensitively in the schema (rule 11 — never trust the UI's dedupe); GeoNames neighbourhood artifacts parked in Improvements for later.
  LESSON: invariants belong in the query or constraint, not in comments — the `.is()` guard costs one clause and makes the race unrepresentable, where the read-then-write needed a comment promising what nothing enforced. And a swallowed error object is a future audit finding by definition: capture it (Sentry) even when the user-facing message stays generic.
- 2026-07-11 · AUDIT #4 resolved (all four findings, same session):
  (1) MED open redirect — centralized the validation in a new `lib/auth/redirect.ts` `safeRedirectPath()`: a client-supplied `?next=` survives only if it is a same-origin absolute path (single leading `/`, rejecting `//host`, any `\` — which the WHATWG URL parser rewrites to `/` — and C0 control chars like an embedded tab that the parser strips before parsing); everything else falls back to `/home`. Both `/auth/confirm` and `/auth/callback` route through it, so the future Google OAuth callback inherits the check for free. PROVEN behaviorally, not just by types: `scripts/open-redirect-probe.mjs` mints real single-use token_hashes via the admin API and drives the live route — the audit's own two exploit probes (`next=https://evil.example`, `next=//evil.example`) now land on `/home`, and a legit `next=/check-inbox` still works (3/3 PASS).
  (2) LOW trigger fragility — migration `20260711032148_tolerant_age_confirmed_parse.sql` replaces the hard `::boolean` cast (which aborted the ENTIRE auth.users insert on any unparseable value like "maybe") with a tolerant membership test: truthy spellings → true, everything else → false. Approved by Adnane as auth+RLS SQL (rule 13) before apply. PROVEN: a 5-case admin-API trigger test — junk "maybe" now inserts with age_confirmed=false instead of aborting, real boolean true still yields true, absent key → false (5/5 PASS).
  (3) LOW signInAction — now honors the middleware-stashed `?next=` (hidden form field → validated through the SAME safeRedirectPath()) instead of hardcoding `redirect("/home")`; correct destination once more routes than /home are protected, and no new redirect hole because it reuses the one validator.
  (4) INFO — dropped the unused `_opts` param in `lib/llm/hosted.ts`, clearing the eslint warning.
  LESSON: one shared redirect validator beats per-handler checks — the OAuth callback would otherwise re-grow the same hole the moment it ships; the ROADMAP 1.1 OAuth follow-up is now gated on using safeRedirectPath() + re-running the probe. And a SECURITY DEFINER trigger fires on EVERY insert path (admin API, future OAuth), not just the Zod-guarded form, so it must tolerate junk rather than trust an upstream validator it can't see.
